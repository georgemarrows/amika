T-30100 Search

Cmd-K search for fast navigation across Japanese learning content

The first version should make kanji and word lookup feel instant, while leaving a clean path toward sentence, translation, exercise, and fuzzy full-text search later.

Now: kanji + words Now: simple JSON response Later: sentences + texts Later: FTS5 / semantic search

Decision Summary

T-30100 should use a small set of explicit SQL queries and merge/rank the results in TypeScript. We do not need streaming, parallel query execution, or SQLite FTS for the first implementation.

Search should feel like VS Code Cmd-K: type a short query, see the most navigationally useful matches immediately, use arrows/Enter to open the top result.

What T-30100 Needs Now

1
Exact kanji
If the user types 勉, return the kanji entry 勉 first.
2
Exact words
If the user types a whole expression like 勉強 or する, return that word near the top.
3
Word expression prefixes
If the user types 勉, also return words beginning with it, such as 勉強, 勉強する, and the first several other prefix matches.
4
Reading and English matches
Useful for hiragana and English input. べん should find 勉強. study should find words whose meaning contains study.

Expected Query Shape

Keep SQL boring and small. Run a few bounded queries in series, then merge and dedupe in application code. 

-- 1. exact kanji
select literal, primary_meaning
from kanji
where literal = ?;

-- 2. exact word
select id, expression, reading, primary_meaning
from words
where expression = ?;

-- 3. word expression prefix
select id, expression, reading, primary_meaning
from words
where expression like ? || '%'
  and expression <> ?
order by length(expression), expression
limit 10;

-- 4. reading / English
select id, expression, reading, primary_meaning
from words
where reading like ? || '%'
   or primary_meaning like '%' || ? || '%'
limit 10;

API Shape

Return one finite JSON response. Streaming JSONL/SSE is possible, but not needed yet because these queries should be tiny and fast. 

GET /api/search?q=勉

{
  "query": "勉",
  "items": [
    {
      "type": "kanji",
      "id": "勉",
      "title": "勉",
      "subtitle": "try hard"
    },
    {
      "type": "word",
      "id": "word-id",
      "title": "勉強",
      "subtitle": "べんきょう · To study"
    }
  ]
}

Example Behaviors

Query Expected high-ranking results
勉 kanji: 勉, then words beginning with 勉, especially 勉強.
勉強 word: 勉強, then longer expression prefixes like 勉強する.
べん Words whose readings start with べん, such as 勉強.
study Words whose English meaning includes study, then later sentences/translations containing study.

Performance Position

  • The current data size is small enough that serial queries should be snappy.
  • Use indexes already present on kanji.literal, words.expression, and words.reading.
  • Limit each tier, usually around 10 results.
  • Debounce client input lightly, around 50-100ms.
  • Cancel or ignore stale requests as the user keeps typing.

Why Not Stream Now?

  • JSONL/SSE would add client parsing, partial states, and awkward error handling after partial output.
  • The complete result should arrive quickly enough that partial delivery will not materially improve the UX.
  • If search later becomes heavy, prefer a search projection table or FTS before protocol complexity.

Future Ideas

A
Search all content
Add sentences, translations, text titles, book exercises, grammar examples, and topics below kanji/word results.
B
Search projection table
Create a unified search_documents table with entity type, entity id, title, Japanese body, reading text, English body, and ranking bucket.
C
SQLite FTS5
Use FTS5 for longer English and content fields. Use trigram tokenization for Japanese sentence substring search. Keep direct SQL for one-character kanji and short Japanese queries.
D
Better fuzzy search
Later layers could include kuromoji tokenization, typo tolerance, aliases, romaji normalization, or semantic embeddings.
